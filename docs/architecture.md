# 部署演进与一致性设计

本文区分**当前实现**与**未来目标**。当前使用 SQLite WAL、一个连接和数据目录文件锁，只能运行一个 Auth 写实例；没有实现 PostgreSQL、Redis、Kubernetes 多副本或跨地域多写。新加的资料版本检查、事务统计和索引是迁移准备，不使 SQLite 具备集群能力。

## 当前数据与访问边界

- 核心身份：`users` 保存邮箱、显示名称、角色、停用状态和认证材料。
- 自述资料：`user_profiles` 保存组织、部门、职位、地区、电话、简介、语言与时区偏好。电话未经验证，不可作为认证或账户恢复凭据。资料由本人更新；管理员可以查看。
- 管理员画像：`user_annotations` 保存最多 12 个内部标签及备注。仅管理员查看和编辑；标签不授予权限。角色变更走原权限接口。
- 行为画像：`user_activity_daily` 按用户、应用、UTC 日期聚合成功登录次数及首次/最近访问时间；心跳和登录与会话修改处于同一事务。注销、撤销、过期会话不会删除历史。
- 不采集生日、性别、身份证、精确定位和浏览器指纹。不加载远程头像，不把资料或内部备注返回给第三方 API；需要头像时，未来使用受控上传与尺寸限制。邮箱验证、手机号验证应另设具有过期和防重放机制的流程，不能由个人资料字段自报为“已验证”。
- 当前角色为全局角色；部门、组织和标签均不等于租户、应用成员或应用访问白名单。未来若需要租户隔离，新增租户和成员关联表，并在每个查询中校验租户边界，不能直接以自填组织作为权限依据。

资料和内部标签保存携带 `expected_revision`。更新使用 `WHERE revision=?` 原子条件并递增版本，冲突返回 409，前端提示重新加载。其他安全操作仍遵循当前数据库事务和一次性凭据规则。

## 统计口径与可解释性

- 日历和图表使用 UTC，最后 30 个自然日含当天；7 天同理。这不是滚动 168/720 小时。界面显示本地时间戳不改变分组。
- “活跃用户”指成功登录或认证后的有效心跳用户；多设备、多应用按用户去重。普通 API 读取不自动计为活跃，接入方须持续调用心跳。无效/过期凭据不会写活跃记录。
- “在线”指账户未停用、会话未过期，且最近 120 秒有心跳或成功登录；不是网络在线探测，也不是页面实际停留时长。
- 活跃历史包含后来被停用的用户；“当前在线”排除停用账户。登录次数包含控制台和第三方成功登录，不包含失败登录。
- 全局分析与单用户详情使用同一只读事务快照。用户目录单次请求的总数和分页来自同一事务；不同页面请求间发生新注册时，偏移分页仍可能变化。
- 应用分布最多 20 项，单用户会话和审计最多 50 项；界面明确标注限制。不把条目数量宣称为无限范围的总量。
- 升级会从**已保留**的登录审计和现存会话回填。现存会话只证明最近心跳当日活跃；不能推测两次心跳之间的访问，更不能推测已删除会话的历史。
- 聚合与审计目前不自动过期。上线前按业务和隐私要求确定保留周期；现有数据无自动删除任务。未来只给聚合任务和明确的清理任务增加 TTL，不可让 TTL 改变 Token / 2FA 的安全语义。

## 阶段一：网关 + 单 Auth 实例（现在）

```text
客户端 → HTTPS 网关 / 负载均衡器 → 单 Auth 实例 → 本地持久卷 SQLite
```

网关可以多副本，但后端仍然只有一个 Auth。不要通过复制数据卷、NFS/共享 WAL、定时复制数据库或取消文件锁来扩容。多个各有 SQLite 的容器会产生互不一致的用户、会话和防重放状态。

网关仅转发配置的公开域名，保持 `AUTH_PUBLIC_URL` 与 HTTPS 实际访问地址一致、`AUTH_SECURE_COOKIE=true`；不要扩大 Origin 白名单。健康检查使用 `/healthz`，公开 JSON 探针使用 `/health` 或 `/api/health`。

目前**不信任** `X-Forwarded-For`。代理后审计 IP 是连接到应用的代理 IP，进程内每分钟 30 次限流也由代理后的用户共享。生产规模增大前应先在可信网关执行防滥用策略，并设计应用的显式可信代理 CIDR 配置；只在直连对端受信任、网关覆盖用户传入头且已移除入口绕过路径时解析代理链。不能仅因某个头存在就信任它。

建议测量认证延迟、SQLite 等待、健康失败、限流率、心跳写入量、数据卷空间和备份恢复时间。当前未提供 Prometheus 端点及 SLO 告警；这些属于后续工作。

## 阶段二：同地域多 Auth 副本（实施前置条件）

```text
客户端 → HTTPS 网关 → Auth A / Auth B / Auth C
                         ├→ PostgreSQL 主库（身份、会话、安全状态）
                         ├→ Redis（共享限流，可选缓存）
                         └→ KMS / Secret 管理（统一解密密钥）
```

1. 实现数据库适配和 PostgreSQL 迁移，保留唯一索引、外键、事务；SQL 方言和占位符不能简单替换。先做独立新库迁移和停服切换验证，再启用多副本。保留原 SQLite 和主密钥备份，不能让两个数据库同时接受身份写入。
2. 用户、角色/停用、Key 撤销、会话、TOTP 时间步、备用码和找回 Token 均以同一主库为事实来源。校验后消耗凭据用条件更新/删除并检查影响行数；并发处理时只能一个成功。
3. 会话始终可撤销；沿用服务端会话存储，不靠负载均衡粘性会话维持安全，也不把长期自包含 JWT 当作撤销机制。权限校验不读取有复制延迟的从库。
4. Redis 负责跨进程原子限流（例如 Lua + 过期），并区分可信来源、账户摘要和应用等维度。Redis 故障时认证入口应拒绝或采用经评审的严格降级；不能无限放行。当前进程内限流并非此实现。
5. 所有副本使用同一套加密密钥及 Key ID；现有单个 `master.key` 迁移到 Secret/KMS 前需验证每个副本能够解密。不能各自生成不同主密钥。轮换需保留解密旧数据能力，不将密钥打包进镜像。
6. 安全写入和审计使用事务；需要异步通知或分析时写同库 outbox，消费者使用唯一事件 ID 去重，失败可重试。活跃分析可最终一致，但不能以分析延迟影响安全决策。
7. 心跳可在每用户/应用/分钟内合并并单独测压。保留会话期限和单次凭据的同步强一致路径；不把最终一致缓存当作在线撤销依据。
8. 部署前以串行 migration job 升级数据库，多副本只做版本校验；使用兼容窗口的 expand/contract 迁移。给连接池、网关超时、就绪探针和优雅停机定义明确上限。当前 `/healthz` 是数据库探针，不能直接声称已区分 liveness/readiness。

## 阶段三：多集群 / 多地域

优先采用**单写地域 + 灾备地域**：只有写地域处理认证与凭据消耗。其他地域通过网关路由到写地域；公共静态资源可多地域缓存。跨地域只读副本可以用于允许延迟的分析，不能用来决定停用、撤销或 OTP 是否已经消费。

故障切换必须先隔离旧主（fencing），再提升唯一新主；仅改 DNS 不能防止网络分区下双主。异步复制可能丢失已确认的安全状态，导致恢复 Token 或备用码重放，不能在未评估 RPO 时承诺“零数据丢失”。需要零丢失的身份状态须采用跨故障域同步提交 / 共识存储，并接受网络延迟及不可用时拒绝认证的代价。时钟必须可靠同步。

真正跨地域多写需要全局唯一身份目录、邮箱唯一约束、线性一致凭据消费与撤销传播设计；常见最终一致多主复制不满足这些条件。上线前单独立项，不通过当前 Compose 扩副本实现。

## 进入多实例前的验收清单

| 场景 | 必须验证的结果 |
| --- | --- |
| 两个副本同时使用同一 TOTP / 备用码 / 找回 Token | 仅一次成功，重放被拒绝 |
| A 停用用户或撤销 Key，会话下一请求落到 B | B 即刻拒绝，不能等待缓存 TTL |
| 更新密码 / 找回密码 / 启用 2FA 后切换副本 | 现有会话失效规则保持一致 |
| 同邮箱并发注册、并发修改资料 | 唯一账户；资料冲突 409，不静默覆盖 |
| 客户端伪造代理头、绕过网关 | 不能伪造审计来源或绕过共享限流 |
| Redis / 数据库 / 跨地域链路故障 | 有明确拒绝策略，无双主、无跳过认证 |
| 时钟偏差、主库切换、消费者重试 | OTP 不被重复消费，分析不重复计数 |
| 更新中断和数据库迁移后健康失败 | 不回滚旧结构；只向前恢复兼容镜像 |
| 灾备演练 | 验证备份恢复、密钥解密、RPO/RTO 和写主隔离 |

以上是未来架构的验收门槛，不是当前版本已经完成的集群测试。
